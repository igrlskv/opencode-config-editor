# opencode-config-editor

GUI-плагин для **OpenCode Desktop**: просмотр и редактирование конфига OpenCode прямо из интерфейса,
управление моделями провайдера (поиск, добавление/удаление одним кликом, выбор модели по умолчанию)
и валидация конфига.

> Плагин использует экспериментальный GUI API OpenCode (`@opencode/plugin/gui`) и рассчитан на
> OpenCode Desktop 2.3+. API может меняться между релизами — см. «Совместимость» о поддерживаемых
> версиях и что делать после обновления OpenCode.

## Возможности

- **Два скоупа конфига**: глобальный (`~/.config/opencode/opencode.json`) и проектный
  (`<проект>/opencode.json` или `<проект>/.opencode/opencode.json`). Переключение селектором;
  если у проекта ещё нет конфига — кнопка «Создать конфиг проекта».
- **Каталог моделей провайдера**: по умолчанию RouterAI (`https://routerai.ru/api/v1/models`,
  ~600 моделей). Ключ берётся из глобального конфига (поддерживаются литеральный ключ, `{file:…}`
  и `{env:…}`) или из переменных окружения `ROUTERAI_API_KEY` / `OPENROUTER_API_KEY`.
- **Контекстный поиск**: живой фильтр по id, имени и вендору с релевантностью
  («glm», «deepseek flash», «claude sonnet» …).
- **Добавление/удаление одним кликом**: тумблер у каждой модели. Отмечено = модель есть в
  `provider.<id>.models` выбранного файла. Перед каждой записью — валидация.
- **Модель по умолчанию**: кнопка «Сделать по умолчанию» пишет поле `model: "<провайдер>/<модель>"`.
- **Raw-редактор**: правка файла как обычного JSON; «Форматировать», «Сохранить» (сначала валидация),
  «Обновить». Сохранение с ошибками блокируется. Подсветка синтаксиса JSON, нумерация строк,
  история undo/redo (CodeMirror 6).
  Несохранённый текст в редакторе (черновик) имеет приоритет над файлом: валидация и «Сохранить»
  работают с ним. Черновик создаётся только вашими правками (печать, вставка, undo) и очищается
  после любой записи через плагин («Сохранить», тумблер, «Сделать по умолчанию», создание конфига) —
  поэтому тумблер + «Сохранить» не «воскрешают» старое содержимое.
- **Валидация**: по официальной JSON-схеме (`https://opencode.ai/config.json`, встроена в плагин) плюс
  собственные правила — см. раздел «Валидация».
- **Панель в сессии**: вкладка «Конфиг» в боковой панели открытой сессии — тот же редактор, не выходя
  из чата (см. раздел «Панель в сессии» ниже).
- **Живые обновления**: плагин следит за файлом и подхватывает внешние правки (в том числе сделанные
  агентом в сессии); бэкап `.bak` рядом с файлом перед каждой записью; запись атомарная (tmp + rename).

## Установка

> **Для новичков** — пошаговая инструкция с тремя способами установки (ZIP с GitHub /
> Release / git clone) и подробными путями для Windows/Linux/macOS: [INSTALL.md](INSTALL.md).
> Ниже — краткая версия.

### Вариант 1: локальная папка (этот репозиторий)

1. Соберите плагин:

   ```sh
   bun install
   bun run build
   ```

   Нужен [bun](https://bun.sh) (`curl -fsSL https://bun.sh/install | bash`). Подойдёт и node+npm:
   `npm install && npm run build`.

2. Подключите папку в **глобальном** конфиге `~/.config/opencode/opencode.json`
   (именно глобальном — Desktop-приложение читает только его):

   ```jsonc
   {
     // …ваш существующий конфиг…
     // путь — там, куда вы положили папку плагина (абсолютный)
     "plugins": ["/path/to/opencode-config-editor"]
   }
   ```

3. Откройте/переоткройте OpenCode Desktop. Плагин появится в **Settings → Extensions → Plugins**,
   а его страница — в **Settings → Config Editor** (иконка шестерёнки). Быстрый доступ: палитра
   команд → «Открыть редактор конфига».

### Вариант 2: npm-пакет (после публикации)

```jsonc
// ~/.config/opencode/opencode.json
{
  "plugins": ["opencode-config-editor"]
}
```

## Совместимость

| Версия OpenCode Desktop | Статус |
|---|---|
| **2.3.x** | ✅ Поддерживается. Разработка и проверка — на 2.3.0. |
| **2.2.x и старше** | ❌ Не работает: GUI-плагин API появилось позже. |
| **новее 2.3.x** | ⚠️ Не проверено: экспериментальное API может измениться. |

Плагин собран против официального SDK `@opencode/plugin` **2.3.0** (версионируется синхронно с
приложением). GUI-часть использует экспериментальный API (`gui-experimental`), который не даёт
гарантий совместимости между релизами.

**После обновления OpenCode:**

1. Откройте панель «Конфиг» или Settings → Config Editor — если плагин отрисовался, всё в порядке.
2. При несовместимости вы увидите красный фолбэк «Плагин не смог отрисоваться» с кнопкой
   «Повторить» вместо пустого места; точное место падения — в логе приложения
   (`renderer.log`, искать `config-editor render crash` — там стек).
3. Типичный ремонт: обновить зависимость `bun update @opencode/plugin` (или указать новую версию
   в `package.json`), пересобрать `bun run build`. Если host поменял API — правки минимальны:
   весь доступ к нему сосредоточен в `src/gui/window.tsx` и `src/gui/settings.tsx`.
4. Полный откат без пересборки: убрать плагин из `plugins` в глобальном конфиге.

## Перенос на другие машины (Linux, Windows)

Плагин кроссплатформенный: в коде объявлено `os: ["macos", "windows", "linux"]`, файловые операции
и пути строятся через `node:path`/`node:os`, а путь к глобальному конфигу на Windows определяется
автоматически (`%APPDATA%\opencode\opencode.json`, с фолбэком на `~/.config/opencode`).

### Способы переноса плагина

| Способ | Действия на новой машине |
|---|---|
| **Копирование папки** | Скопировать папку проекта (минимум `dist/gui-experimental.cjs` и `package.json`), указать её путь в `plugins` глобального конфига. Сборка не нужна. |
| **Git** | Закоммитить репозиторий (без `node_modules`), на новой машине `git clone` → `bun install && bun run build` → путь в `plugins`. |
| **npm (для 3+ машин)** | Один раз опубликовать (см. «Публикация»), на каждой машине `"plugins": ["opencode-config-editor"]`. Обновления — `opencode plugin update`. |

### Что в конфиге не переносится как есть

- `"plugins": ["/path/to/..."]` — абсолютный путь одной машины; на каждой укажите свой
  (или используйте npm-вариант, где путь не нужен).
- `"apiKey": "{file:/path/to/credentials}"` — абсолютный путь до файла с ключом; на новой машине создайте
  свой файл с ключом и укажите его, либо перейдите на `{env:ROUTERAI_API_KEY}`.
- Сам API-ключ — **не коммитьте его** в git и не копируйте открытым текстом между машинами
  (мессенджеры, почта). Передавайте защищённым каналом или задавайте на месте.

### Рекомендуемая схема для нескольких машин

1. **Проектный конфиг** (`<проект>/opencode.json`) — свободно в git: плагин не пишет туда ключи,
   и валидатор предупредит, если ключ попал литералом.
2. **Глобальный конфиг** — свой на каждой машине: провайдер, `"apiKey": "{env:ROUTERAI_API_KEY}"`,
   и `plugins` с локальным путём или именем npm-пакета.
3. **Ключ** — переменная окружения на каждой машине:
   - macOS/Linux: `export ROUTERAI_API_KEY=sk-…` (в `~/.zshrc` / `~/.bashrc`), либо `{file:…}`
     на локальный файл с правами `600`;
   - Windows: `setx ROUTERAI_API_KEY "sk-…"` (переменная пользователя; перезапустите OpenCode после задания).

### Чек-лист переноса

- [ ] Плагин доставлен (папка / git / npm) и собран, если нужно
- [ ] В глобальном конфиге: `plugins` указывает на плагин; путь локальный или npm-имя
- [ ] Ключ доступен: `ROUTERAI_API_KEY` в окружении или `{file:…}` на существующий файл
- [ ] Открыть OpenCode Desktop → **Settings → Extensions → Plugins** → плагин в статусе **active**
- [ ] Открыть страницу **Config Editor**: глобальный файл найден, каталог моделей загружен


## Настройки плагина

Передаются через объектную форму в `plugins`:

```jsonc
{
  "plugins": [
    {
      "package": "/path/to/opencode-config-editor",
      "options": {
        "providerID": "routerai",
        "catalogURL": "https://routerai.ru/api/v1/models"
      }
    }
  ]
}
```

| Опция | По умолчанию | Описание |
|---|---|---|
| `providerID` | `"routerai"` | Провайдер по умолчанию: стартовый выбор в селекторе провайдеров; при единственном провайдере в конфиге — тот, с кем работают тумблеры |
| `catalogURL` | `https://routerai.ru/api/v1/models` | OpenAI-совместимый эндпоинт каталога (`GET`, Bearer-авторизация); общий для всех провайдеров |

> Привязки к конкретному провайдеру нет: `providerID`/`catalogURL` — лишь дефолты, подходят
> любые OpenAI-совместимые. Например, для OpenRouter: `"providerID": "openrouter"`,
> `"catalogURL": "https://openrouter.ai/api/v1/models"`.

## Как пользоваться

1. **Выберите файл**: селектор «Файл конфига» — «Глобальный» или «Проект». Проектный доступен,
   когда в этом приложении открыта сессия в проекте.
2. **Выберите провайдера**: если в конфиге объявлено несколько провайдеров (`provider`/`providers`),
   над списком моделей появится селектор — тумблеры и «Сделать по умолчанию» работают с выбранным.
   С одним провайдером селектор не показывается. Провайдеров в конфиге нет — подсказка «добавьте
   через "JSON целиком"».
3. **Найдите модель**: строка поиска фильтрует каталог по подстрокам; пробел = «И»
   (например `deepseek flash`).
4. **Покажите только подключённые**: кнопка «Только подключённые (N)» над списком фильтрует каталог
   до моделей, включённых в текущий конфиг. Работает вместе с поиском; N — число моделей в конфиге
   (совпадает со сводкой секции). Модели, есть в конфиге, но отсутствующие в каталоге (удалены
   на сервере), в отфильтрованном списке не показываются — их видно в «JSON целиком».
5. **Включите/выключите модель**: тумблер справа. Плагин сразу (после валидации) пишет файл.
6. **Назначьте дефолт**: кнопка «Сделать по умолчанию» у включённой модели.
7. **Правьте руками** при необходимости: раздел «JSON целиком».

> Про каталог: он один для всех провайдеров и берётся из настроек плагина (`catalogURL`,
> по умолчанию RouterAI). Если выбранный провайдер — не тот, чей каталог загружен, его моделей
> в списке не будет (они не значатся в каталоге): добавляйте такие модели через «JSON целиком».
> Подсказка об этом показывается под списком.

### Проектный конфиг и мердж

Проектный конфиг мерджится поверх глобального, поэтому в нём достаточно добавить только модели:

```jsonc
// <проект>/opencode.json
{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "routerai": {
      "models": {
        "z-ai/glm-5.3-flash": { "id": "z-ai/glm-5.3-flash", "name": "GLM-5.3-Flash" }
      }
    }
  }
}
```

`baseURL`, ключ и заголовки подтянутся из глобального конфига. Плагин **не пишет API-ключи** в
проектный конфиг и предупреждает, если ключ вписан туда литералом (риск попадания в git).

## Панель в сессии

Кроме страницы настроек, редактор доступен **внутри сессии** — вкладкой в боковой панели рядом
с чатом. Это удобно для проектного конфига: сессия уже смонтирована, и скоуп «Проект» доступен
сразу, без проверки «есть ли открытая сессия».

**Три способа открыть:**

1. **`+`-меню боковой панели** (слева от поля ввода, рядом с вкладками панели) → «Редактор конфига».
2. **Горячая клавиша** `Cmd+Shift+C` (Windows/Linux: `Ctrl+Shift+C`) — команда «Открыть редактор
   конфига здесь». Переопределяется в настройках клавиш приложения.
3. **Палитра команд** — команда с тем же названием.

Вкладка называется «Конфиг», ведёт себя как обычная вкладка панели: закрывается крестиком,
восстанавливается через «Недавно закрытые» (⌘⇧T), положение в полосе можно перетаскивать.
Ширина панели для этой вкладки — 520px, её можно сузить/расширить перетаскиванием.

Внутри — тот же интерфейс, что на странице настроек: селектор скоупа, модели, JSON-редактор,
валидация. Содержимое не дублируется между панелью и страницей настроек — оба входа работают
с одними и теми же store'ами (черновик, свёрнутость секций, выбранный скоуп общие).

> Скролл: хост не прокручивает содержимое панели — панель делает это сама (обёртка
> `height: 100%` + `overflow-y: auto`, `overscroll-behavior: contain`, чтобы скролл
> не «протекал» в чат). На узких экранах (<768px) хост показывает мобильное
> представление панели.

## Валидация

Каждое сохранение и каждый тумблер проходят валидацию:

1. **Синтаксис JSON** — с понятным сообщением об ошибке.
2. **JSON-схема** — официальная схема OpenCode (встроена в плагин): типы полей, `enum`, `pattern` и т.д.
3. **Собственные правила**:
   - `model` должен быть вида `провайдер/модель[#вариант]`, и такая модель должна существовать
     в объединённом (глобальный + проектный) конфиге;
   - провайдеры, упомянутые в файле, должны быть определены в объединённом конфиге;
   - каждый элемент `enabled_providers` должен существовать;
   - ссылки `{file:/путь}` должны указывать на существующие файлы;
   - *(для проектного конфига)* предупреждение при литеральном API-ключе вместо `{file:…}`/`{env:…}`.

Ошибки и предупреждения показываются в блоке «Валидация» (его сводка видна даже в свёрнутом виде,
а при ошибках блок раскрывается сам) и блокируют сохранение (предупреждения — нет).

## Структура проекта

```
├── CONTINUATION.md          # памятка для продолжения работы (контекст, решения, чек-листы)
├── README.md
├── package.json             # exports: "./gui-experimental" → dist/gui-experimental.cjs
├── vite.config.ts           # пресет gui() из @opencode/plugin/gui/vite
└── src/
    ├── gui.tsx              # вход: Plugin.define({...definition, setup, main})
    └── gui/
        ├── definition.ts    # декларации: os, stores, i18n (en + ru)
        ├── i18n.ts          # тексты интерфейса
        ├── contract.ts      # типизированный IPC main ↔ окно (Effect Schema)
        ├── main.ts          # Electron main: fs (атомарная запись, .bak), каталог, watch
        ├── validate.ts      # ajv + собственные правила
        ├── search.ts        # релевантный поиск по каталогу
        ├── schema/config.schema.json  # официальная схема конфига OpenCode
        ├── window.tsx       # setup: страница настроек, панель сессии, команды, меню
        └── settings.tsx     # UI страницы (используется и в настройках, и в панели)
```

### Архитектура

GUI-часть плагина выполняется в двух процессах OpenCode Desktop:

- **`main`** (Electron main) — единственное место, где работают файловые операции и внешние запросы:
  чтение/атомарная запись конфига, `.bak`, наблюдение за файлом (`fs.watchFile`), загрузка каталога
  моделей с Bearer-ключом из конфига, валидация (нужен доступ к ФС для `{file:…}`).
- **`setup`** (каждое окно) — интерфейс: страница настроек, вкладка боковой панели сессии,
  `+`-меню панели, команды (в т.ч. `mod+shift+c`), поиск, тумблеры, редактор.
  Общение с main — через типизированный IPC (`ConfigIpc`), события `changed` сообщают окну о внешних
  правках файла.

## Разработка

```sh
bun install
bun run watch      # пересборка при изменениях; GUI перезагружается в открытых окнах сам
bun run typecheck  # tsc --noEmit
```

Полезно знать:

- **Settings → Extensions → Plugins** показывает статус плагина и позволяет отключить его GUI.
- Логи сервера: `~/.local/share/opencode/log/opencode.log` (фильтр `role=server`).
- Если плагин не загрузился: проверьте, что `dist/gui-experimental.cjs` существует, и что в
  `opencode.json` указан абсолютный путь.
- Изменение `options` плагина в конфиге тоже перезагружает его.

## Автономность и зависимости

Плагин максимально самодостаточен: весь функционал вшит в один файл `dist/gui-experimental.cjs`
(~860KB), ничего не скачивает при установке и работе (кроме каталога моделей — это данные
провайдера, не код).

**Что вшито в бандл** (переносится вместе с ним, отдельно ставить не нужно):

- CodeMirror 6 + JSON-парсер (редактор с подсветкой)
- ajv + ajv-formats (валидация) и обе JSON-схемы (OpenCode + models.dev)
- поиск по каталогу, весь UI

**Что остаётся внешним и почему** (это требование платформы, а не недоработка):

- `@opencode/plugin/gui`, `effect`, `solid-js` — предоставляет само приложение Desktop.
  Vite-пресет плагинов запрещает их вшивать: копия не разделяла бы состояние с приложением
  и сборка падает с ошибкой.
- `node:fs` / `node:path` / `node:os` — встроенные модули рантайма, «библиотеками» не являются.

**Что нужно для работы** — только файл бандла и `package.json` (последний — чтобы хост прочитал
`exports`). Для npm-варианта зависимости ставятся автоматически из `dependencies`.

**Что нужно только для сборки** — `node_modules` (~300MB с dev-зависимостями: vite, typescript,
типы). На машине, где плагин не пересобирается, они не нужны.

**Страховка ajv-кодогенерации**: некоторые ключевые слова схем заставляют ajv вставлять в
генерируемую функцию `require("ajv/dist/runtime/…")`. Такой код исполняется вне модуля (через
`new Function`), поэтому main-часть плагина заранее публикует `createRequire(__filename)` в
`globalThis.require` — гипотетический require отрезолвится в `node_modules` плагина. Для текущей
схемы конфига этот путь не выполняется (проверено), страховка — на будущее.

## Публикация в npm (для поддерживающих)

1. Уберите `"private": true` из `package.json`, поднимите версию.
2. `bun run build && npm publish` (в `files` уже только `dist`).
3. GUI API экспериментальный: перед релизом проверьте плагин против целевой версии OpenCode.

## Публикация репозитория (GitHub и т.п.)

Репозиторий готов к выкладке «как есть»:

- **Можно выкладывать**: `src/`, `package.json`, `vite.config.ts`, `README.md` — в них нет ключей
  и машинных путей (плагин читает их только из вашего локального конфига).
- **`dist/` обычно не выкладывают** — собирается `bun install && bun run build`; если хотите
  давать пользователям «скачал и подключил», можно и закоммитить (`files` в package.json на
  npm-публикацию это не влияет).
- **Не выкладывайте**: `node_modules`, локальные конфиги с ключами (их в репозитории нет —
  не добавляйте), `CONTINUATION.md` по желанию: это внутренняя рабочая памятка с фактами
  о машине разработки, для пользователей она бесполезна.
- Добавьте `LICENSE` (например MIT) и поле `"license"` в `package.json`, если планируете
  чужое использование.

## Устранение неполадок

| Симптом | Что делать |
|---|---|
| Страницы «Config Editor» нет в Settings | Проверьте `plugins` в **глобальном** `opencode.json`, наличие `dist/gui-experimental.cjs`, статус в Settings → Extensions → Plugins, лог `role=server` |
| «Каталог моделей не загружен» / `error` | Не найден API-ключ: впишите провайдера с ключом в глобальный конфиг или задайте `ROUTERAI_API_KEY`; проверьте доступность `catalogURL` |
| «Нет открытой сессии» | Проектный конфиг доступен только когда открыта сессия в проекте — откройте сессию и вернитесь на страницу |
| Ошибка при сохранении | Смотрите панель валидации; при подозрении на баг — файл `.bak` содержит предыдущую версию |
| Плагин не подхватил правку файла руками | Проверка файла — раз в секунду; нажмите «Обновить» |

## Известные ограничения

- GUI API OpenCode экспериментальный (`-experimental` в имени экспорта) — возможны изменения.
- Дерево моделей показывает каталог провайдера целиком; фильтр по возможностям (vision/tools)
  пока не поддерживается.
- Валидация ориентирована на V2-схему OpenCode; старые V1-поля (`npm` вместо `package` и т.п.)
  допускаются схемой, но часть собственных правил может о них не знать.
- На Windows плагин ищет глобальный конфиг сначала в `%APPDATA%\opencode`, затем в
  `~/.config/opencode`. Если ваша установка OpenCode держит конфиг в другом месте и страница
  показывает «файл не существует» — создайте пустой файл по одному из этих путей или сообщите
  в issue.
